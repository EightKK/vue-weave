# Architecture and scope

The package has three boundaries.

- src/core contains typed graph/interval inputs, validation, graph traversal, layout, time mapping, interval editing, work calendars, scheduling and resource-load analysis. It has no Vue or browser imports.
- src/components owns measurement, SVG/HTML rendering, local camera/scroll state and transient pointer previews. Persistent selection and accepted schedule data belong to the parent.
- examples contains business data and validation. Components do not import examples.

The ESM root exports Vue components and core functions. The separate core export supports headless use. Vite externalizes Vue. Declaration files preserve props, slots and exposed methods. Consumers load style.css explicitly.

## Graph layout

An iterative Kosaraju traversal finds strongly connected components. The condensed graph supplies ranks; nodes in a component occupy the same rank. Input order determines the order within a column. Curves connect adjacent columns, bypass lanes route long edges, and same-rank edges use a side route. TB transposes the geometry while preserving node sizes.

This is a deterministic layout baseline. Dense edge sets and cycles can produce overlapping routes or labels. Because all nodes of a strongly connected component share one rank, a large cycle becomes one long column (one row in TB and BT): a 5,000-node cycle is about 214 by 410,000 units with the default sizes. Callers that expect large cycles can break or filter them first with findGraphCycles, or use layoutForceGraph. By default crossings are not optimized; set crossingReduction to barycenter or median for opt-in sweeps that reorder nodes within each rank (long edges and same-rank edges are not part of the objective). RL and BT mirror the LR and TB geometry. layoutTreeGraph and layoutRadialGraph use a breadth-first spanning forest and route the remaining edges separately. layoutForceGraph runs a seeded, deterministic force simulation (link springs, Barnes–Hut repulsion over an iterative quadtree and gravity), removes box overlaps with grid-based passes and packs connected components in rows. By default all supplied nodes and edges are rendered; applications can use graphNeighborhood to narrow the input, or opt in to viewport culling with cullOffscreen, which renders only the elements that intersect the visible region plus an overscan margin (layout and the minimap still cover every node). Pan/zoom transforms one SVG group without rerunning layout. NetworkGraph builds its geometry in one pipeline: collapseGraphGroups (only with collapsed groups), the layout, the positions and sizes overlays, port routing and finally routeGraphEdges for the edge style and waypoints. Each step returns its input unchanged when it has nothing to do, so the default output is the layout's own. Previews of node drags, resizes and waypoint drags do not change props. They reuse the saved geometry and recompute only the boxes of the changed nodes and the routes of their edges, with the same results as rerunning the overlays and routing for the whole graph. Port routes are clamped to the layout size, so when a preview changes that size the other port edges whose control points reach past the smaller of the two sizes are rerouted too. Group frames are recomputed only for the groups that hold a changed node, the groups whose own nodes reach past the smaller size, and their ancestors. Each node, edge, minimap rectangle, connection handle and group frame is an internal functional component that reads its box, path or frame from a ref of its own, so a preview re-renders only the items of the changed nodes and edges; the item lists render again only when the rendered set, selection, dimming, the connection draft or other item props change. Still proportional to the graph per move: with groups, one pass over the group list (frame list, content bounds and, with culling, the near-view test), which grows with the number of groups but not with their members; with `alignmentGuides`, the guide search over the other node boxes; with waypoints, a check of the edges that have them; and any camera move during the drag (auto-pan), which culls and redraws as a pan does.

## Timeline rendering and editing

A single horizontal/vertical scroll surface contains the fixed header, sticky row labels and positioned bars. Visible row indices plus overscan determine row DOM. Visible time bounds limit bar and tick rendering. Dependency paths are computed in the same coordinate system. The renderer uses fixed row heights and explicit lanes.

Row virtualization bounds DOM size. Input validation, row indexing and dependency scanning still process input collections. Each visible row's bars are filtered against the time window. The included 1,000-row example demonstrates rendering behavior; it is not a performance guarantee for arbitrary data sizes or devices. Browser maximum scroll dimensions also bound very large axes.

A pointer edit records the accepted interval and the initial pointer coordinate. Subsequent movement produces a local preview. Capture keeps the gesture attached to the bar; cancellation clears the preview. Source-data or coordinate changes cancel in-flight edits. On commit, validateEdit runs and an accepted proposal is emitted. The parent owns the resulting state.

Progress drags, bar deletion and the context menu use the same contract. A progress drag previews the fill locally and proposes the snapped value on release; Delete proposes bar IDs; a context menu event only describes its target. The parent applies or ignores each proposal. Tooltips are transient view state that exists only after mounting, so server output never contains them.

Drag to create and cascades follow it too. A create drag captures the pointer on the scroll container, previews a local interval and proposes a `TimelineCreate` that the parent turns into a bar with its own ID. A `cascade` callback is application code that the chart calls synchronously when a dragged bar reaches a new snapped interval; its result is only drawn as ghost outlines and attached to the proposal as one batch, so the chart still never schedules or changes bars itself. The previews share one conditional with the link preview and the add buttons share one with the expand toggle, which keeps the server markup of charts without these props unchanged.

Calendar-derived overlays are display data, not scheduling logic. Non-working shading, critical outlines, float lines, deadline indicators and bar segments are drawn from `nonWorkingPeriods` and optional bar fields that the application computes, typically with `invertWorkPeriods` and `scheduledBarFields`. Shading, float lines and deadline indicators are filtered against the visible time window like bars. A move preview shifts a bar's segments by the previewed displacement; a resize preview drops them, since only the scheduler knows the new work pattern.

Scheduling constraints on bars are display data with an editing contract like the progress slider's. The chart draws each constraint, marks the ones that the bar's dates break and, with `constraintsEditable`, previews a handle drag locally and proposes a `TimelineConstraintEdit`; it never checks feasibility or moves a bar. The application applies the proposal (`applyTimelineConstraintEdit`) and reschedules with `scheduleTasks`, which reports a conflict. Markers and handles share the deadline list and the handle list, so the server markup of charts without constraints is unchanged.

## Supported scope

The timeline supports fixed-height rows, collapsible row trees, explicit lanes and continuous invertible time scales. Timeline baselines and header bands come from application data. A bar can carry several named baseline sets; up to three are drawn as stacked strips that the bars make room for, so rows keep their fixed height. A collapsed group hides descendant bars and their links. Applications can provide a parent bar or display an aggregated descendant interval with showSummaries. The same rollup feeds extra column values.

Graph movement applies an overlay of absolute coordinates over the base layout. The SVG and minimap share the same geometry. Incident paths are recomputed during preview. The original node and edge arrays remain owned by the caller. Grouped moves, reconnection and deletion emit proposals, which let the caller accept each edit as one history entry. The context-menu event and the tooltip slot leave the menu and the tooltip content to the application; the component only reports targets and positions the tooltip overlay.

The default renderer handles text, SVG and HTML. Slot authors own content dimensions and accessibility of custom content. Keyboard selection and interval editing are included; assistive-technology testing with dedicated screen readers is still needed before claiming broad accessibility conformance.

Scheduling and resource-load analysis are explicit core operations called by the application. The chart renders accepted results. Capacity conflicts are diagnostic. `levelResources` provides a baseline priority-based leveling heuristic; setup sequencing and optimization policies remain the application's concern. Calendar generation uses a fixed UTC offset or an IANA time zone with daylight-saving rules from `Intl`. See [Scheduling and resource load](scheduling.md).

## Export

SVG export is a pure core operation. `renderGraphSvg` and `renderTimelineSvg` build a standalone document string from data, a layout or time scale and an explicit theme, so they run in Node, workers and tests. The components only gather their current props, collapsed rows, zoom and the computed `--vw-*` colours and call those builders. PNG export is the one browser-only step: the SVG is loaded into an image, drawn on a canvas and encoded with `toBlob`, after a size check. Export uses the default rendering because slots render arbitrary DOM that a string builder cannot reproduce.

## Right-to-left layout

GanttChart measures every horizontal position from the inline-start edge of the time axis. In right-to-left mode the same offsets are written as `right` instead of `left`, the scroll offset is read as the distance from the inline start (`-scrollLeft` in a right-to-left scroll container), and pointer deltas are negated. The time scale itself is not mirrored, so `toX`/`toTime` round trips, snapping and edit proposals are identical in both directions. SVG layers (dependency paths and their hit areas) are flipped with a CSS transform. The SVG exporter has no CSS, so it mirrors the axis with `mirrorTimeScale` instead. NetworkGraph geometry is direction-independent; only the controls and label alignment change.
